# Inventory Service

## 1. Функциональные возможности

### 1.1. Управление количеством продуктов
- **Хранение количества продукта** – сервис должен хранить текущее количество доступных товаров.
- **Списание товара** – при оформлении заказа система уменьшает количество доступных товаров.
- **Возврат товара при отмене заказа** – если заказ отменяется, система должна корректировать количество товаров.
- **Обновление количества товара** – админ обновляет количество на складе.

## 2. Интеграция с Product Service (Kafka Events)

### 2.1. Событие "Создание продукта"
- **Цель**: сохранить информацию о новом продукте в Inventory Service.
- **Получаемые данные**: UUID продукта, начальное количество.

### 2.2. Событие "Удаление продукта"
- **Цель**: удалить информацию о продукте из Inventory Service.
- **Получаемые данные**: UUID продукта.

## 3. Предоставление актуальных данных о количестве продуктов

### 3.1. Выбор стратегии обновления данных
Ранее предполагалось, что **Product Service** будет запрашивать данные о количестве товаров напрямую из **Inventory Service**. Однако было принято решение хранить количество продуктов в **Product Service** и обновлять их асинхронно.

### 3.2. Отправка событий об изменении количества товара
- **Inventory Service** отправляет события об изменении количества товаров в **Product Service**.
- **Product Service** обновляет у себя данные о количестве товаров на основе полученных событий.  


# 🎯 Требования к Inventory Service

## 📦 1. Хранение количества продуктов
- Используется база данных **PostgreSQL** для хранения информации о количестве товаров.

## 🛒 2. Списание товара при оформлении заказа
- **Актор:** `Order Service` 📩
- **Процесс:**
    1. При оформлении заказа поступает запрос на списание товара.
    2. **Избежание конкуренции при изменении остатка товара:**
        - ✅ **Проверка наличия** перед списанием.
        - 🔄 **Редактирование количества товара** должно учитывать параллельные изменения.
        - 🔁 **Возврат заказа** должен корректно обновлять количество без ошибок.

## 🔄 3. Возврат товара при отмене заказа
- **Актор:** `Order Service` 🔄
- **Процесс:**
    1. Если клиент отменяет заказ, система должна вернуть товар на место(увеличить количество).
    2. ❗ **Важно:** Корректно вернуть продукт на место в системе.

## 🔧 4. Обновление количества товара
- **Актор:** `Администратор` 🛠
- **Процесс:**
    1. Запрос поступает напрямую от клиента.
    2. 💡 Необходимо учитывать конкуренцию при обновлении данных.

## 📢 5. Событие «Создание продукта»
- **Актор:** `Product Service (Kafka)` 📨
- **Процесс:**
    1. Обрабатывается **в фоновом режиме**.
    2. Данные о продукте сохраняются в базе данных **Inventory Service**.

## 🗑 6. Событие «Удаление продукта»
- **Актор:** `Product Service (Kafka)` 🗑
- **Процесс:**
    1. При получении события об удалении продукта **информация о нем удаляется** из системы.

| Поле       | Тип данных | Описание                                                       |
|------------|------------|----------------------------------------------------------------|
| `id`       | `UUID`     | Уникальный идентификатор записи в инвентаре.                   |
| `productId`| `UUID`     | Идентификатор продукта (связь с продуктом).                    |

## ⚠️ Анализ

### Важность предотвращения конкурирующих изменений количества товара

Необходимо предусмотреть ситуацию, когда несколько запросов пытаются изменить количество товара одновременно. Это может происходить в следующих случаях:

1. **При оформлении заказа**:
    - Система должна проверять наличие товара перед его списанием, чтобы избежать ситуации, когда товар уже списан в другом запросе.

2. **При редактировании количества товара**:
    - Если количество товара изменяется (например, увеличивается или уменьшается), нужно избежать конфликтов при параллельных изменениях.

3. **При возврате товара**:
    - При отмене или возврате товара необходимо корректно обновить количество на складе, чтобы избежать ошибок или конкуренции между запросами.

### Проблема с обновлением количества товара

Есть опасения, что если администратор изменит количество товара, а клиент потом вернет товар, это может привести к избыточному количеству товара в системе. Пример:

1. **Клиенты оформили 3 товара**, а общее количество на складе — 10.
2. **Администратор изменяет количество товара на 15**.
3. Если клиент отменяет заказ, количество товара увеличивается до 18 (если не учитывать уже оформленные заказы).

### Решение: Бронирование товаров при оформлении заказа

Чтобы избежать таких ситуаций, товары нужно **бронировать** при оформлении заказа, а не удалять из системы, пока заказ не будет полностью оплачен.

1. **Бронирование товаров**: Когда клиент оформляет заказ, товар **не удаляется из системы**, а просто бронируется. Это позволяет учесть количество товаров, которые уже оформлены, но ещё не оплачены.

2. **Обновление количества товара**: Если администратор изменяет количество товара, учитывая уже оформленные, но не оплаченные товары, система обновит количество, вычитая забронированные товары. Например, если администратор решает обновить количество товара на 15, а уже забронировано 3 единицы, то количество товара будет изменено на 12.

3. **Возврат товара**: Когда клиент решает вернуть товар, его количество **добавляется обратно** в систему.

### Статусы товара

Каждый товар будет отслеживаться в двух состояниях:
- **Доступно для продажи**: товар доступен для оформления заказа.
- **Забронировано**: товар оформлен клиентом, но еще не оплачен.

## 📊 Структура данных для Inventory после обновления

| Поле       | Тип данных | Описание                                                   |
|------------|------------|------------------------------------------------------------|
| `id`       | `Long`     | Уникальный идентификатор записи в инвентаре.               |
| `productId`| `UUID`     | Идентификатор продукта (связь с продуктом).                |
| `inStock`  | `Long`     | Количество доступного товара для продажи.                  |
| `reserved` | `Long`     | Количество забронированных товаров.                        |

## 🔒 О конкуренции изменений данных

При изменении количества товаров важно учитывать возможные проблемы с конкуренцией. Например, если несколько запросов одновременно пытаются изменить количество товара, это может привести к конфликту или ошибке.

Чтобы гарантировать правильную работу системы и избежать таких ситуаций, каждый запрос должен быть атомарным — то есть он должен выполняться полностью или не выполняться вообще. Для этого:

- **Использование блокировок на уровне базы данных** — это самый очевидный способ решения проблемы. Пока один запрос не завершится, другие запросы не смогут вмешаться в процесс.

- В нашем случае мы будем использовать **транзакции PostgreSQL**, которые обеспечат, чтобы пока транзакция не завершится, другие запросы не смогут обновить данные. Это гарантирует, что изменения количества товара будут выполнены корректно и без конфликтов.



## 📦 USE CASE: Списание товара (совершение покупки) — Транзакция

1. **Получаем запрос на совершение покупки продукта**  
   Параметры: `uuid productId`, `quantity`.

2. **Проверяем продукт на существование**
    - Если продукта в системе не найдено, возвращаем ошибку **404**.

3. **Блокируем запись** до тех пор, пока не завершится транзакция.

4. **Проверяем доступное количество товара для продажи**
    - Убедитесь, что `quantity >= inStock`.
    - Если товаров для продажи не осталось, возвращаем ошибку **400**.

5. **Уменьшаем доступное количество товара**
    - Уменьшаем `inStock` на `quantity`.

6. **Убавляем количество забронированных товаров**
    - Уменьшаем `reserved` на `quantity`.

7. **Возвращаем клиенту успех**  
   Операция завершена успешно.

---

## 🔄 USE CASE: Возврат товара (отмена заказа) — Транзакция
1. **Получаем запрос/(событие, было решено что отмена заказа будет поступать через Kafka) на возврат товара**  
   Параметры: `productId`, `quantity`.

2. **Проверяем товар на существование**
    - Если товара нет, завершаем операцию и логируем ошибку.

3. **Блокируем данный продукт** до тех пор, пока не завершится транзакция.

4. **Увеличиваем inStock**
    - Увеличиваем `inStock` на `quantity`.

5. **Уменьшаем reserved**
    - Уменьшаем `reserved` на `quantity`.

6. **Товар успешно вернулся на склад**  
   Операция завершена успешно.



## 🔄 Обновление количества товара — Транзакция

1. **Получаем запрос на обновление продукта**  
   Параметры: `productId`, `long quantity` (новое количество).

2. **Проверяем продукт на существование**
    - Если данных о продукте в системе нет, возвращаем ошибку **404**.

3. **Перед обновлением проверяем переданное новое количество**
    - Если новое количество меньше нуля, возвращаем ошибку **400**.

4. **Блокируем запрос на обновление количества продукта для переданного `productId`**
    - Блокировка предотвратит конфликт с другими запросами, пока операция не завершится.

5. **Проверяем, что переданное количество не меньше чем `reserved`**
    - Если переданное количество меньше забронированного, возвращаем ошибку **400**.

6. **Изменяем количество товара**
    - Новое количество (`new quantity`, `nq`) = переданное количество.
    - Устанавливаем `instock` как `(nq - reserved)`.

7. **Обновляем данные в базе**
    - Сохраняем обновленные данные в базе данных.



## 📦 Обработка событий

### 1. Событие `product-created` — Создание продукта

**Отправляется из Product Service при создании нового продукта.**  
**Данные события:**
- `UUID` — идентификатор созданного продукта.
- `Quantity` — количество продукта.

**Обработка события:**
1. Получаем событие из Kafka.
2. Создаем новый объект (сущность) `Inventory` в системе с полями:
    - `UUID` = UUID, полученный из события (идентификатор созданного продукта).
    - `inStock` = Quantity, полученное из события (количество продукта).
    - `reserved` = 0 (так как продукт еще не забронирован).
3. Сохраняем новый объект `Inventory` в базе данных.

### 2. Событие `product-deleted` — Удаление продукта

**Отправляется из Product Service, когда продукт удаляется.**  
**Данные события:**
- `UUID` — идентификатор удаленного продукта.

**Обработка события:**
1. Ищем в базе данных сущность `Inventory` по `UUID`, полученному в событии.
    - Если сущность с таким `UUID` не найдена, ничего не делаем (хотя это маловероятно, если продукт был создан).
2. Если сущность найдена, удаляем информацию об этом продукте в `Inventory` из базы данных.



## 🚚 Отправка событий об изменении количества товара

Каждая функция, которая управляет количеством продукта, должна отправлять событие продукту об изменении количества. Это включает в себя следующие операции:

1. **Редактирование количества товара**  
   Когда администратор изменяет количество товара, система должна отправить событие с новым количеством.

2. **Списание товара при оформлении заказа**  
   После списания товара при оформлении заказа, необходимо отправить событие с обновленным количеством.

3. **Возврат товара при отмене заказа**  
   Когда товар возвращается после отмены заказа, система должна отправить событие с обновленным количеством товара.

Для передачи данных используется **асинхронный подход через Kafka**, что позволяет эффективно передавать информацию о изменении количества товара без блокировки других операций.  
**Передаваемая информация**: новое доступное количество продукта.



# ⚡ Добавление функциональности для списания товара после оплаты

Когда заказ оформляется, товар резервируется, и его количество временно уменьшается. Однако после того, как заказ будет успешно оплачен, товар должен быть окончательно списан из системы.

Для этого добавлена новая функциональность:

## 1. Окончательное списывание товара из системы

После успешной оплаты заказа сервис оплаты или сервис заказа отправляет событие `OrderPaid` в нашу систему.  
Это событие содержит:
- `UUID продукта` — идентификатор товара, который был куплен.
- `Количество` — сколько единиц товара нужно окончательно списать.

## 2. Обработка события `OrderPaid`

Когда система получает событие:
1. Находит информацию о продукте в базе данных.
2. Уменьшает количество зарезервированных товаров на количество, указанное в событии.
3. Обновляет данные, и товар теперь официально списан из запасов, как проданный.
